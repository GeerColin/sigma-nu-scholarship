# Code and Supabase audit — 2026-09-21

## Assessment and boundaries

The core system is implemented and its ordinary read paths use authenticated, publishable-key Supabase clients. However, passing the existing tests did not establish all of the documented security guarantees. This audit reproduced authorization and data-integrity defects, prepared local corrections, and identified remaining reliability/workflow gaps. **The security corrections are not live. Do not expand the pilot on the assumption that this audit deployed them.**

Starting point: `master`, commit `da57bef` (`Record UI polish deployment status`), tracking `origin/master`. Tracked files were clean initially. The pre-existing untracked screenshots and `roster-import-additional.csv` were preserved. No credentials, roster records, or academic records were copied into this report.

Hosted inspection was read-only. No hosted migrations, configuration changes, fixture insertion, project resets, load tests, pushes, commits, or deployments were performed. The computer-use skill guided read-only Auth configuration inspection and local anonymous browser verification; no hosted accounts were used for cross-member academic testing.

Two new local databases were used: `sigma_nu_audit_20260921` and `sigma_nu_audit_replay_20260921`, in the existing local Supabase Docker database container. Only schema definitions were copied, never application records. Test fixtures are synthetic. pgTAP/probe transactions roll back; the committed concurrency fixtures were removed from the isolated database after the test. The original local application database was not reset or migrated. The temporary browser tab and preview processes were closed.

## Confirmed defects corrected locally

Severity indicates the unfixed impact, not the deployment status. “Reproduced” means a local synthetic test, not exploitation of hosted users. All database corrections below remain proposed hosted changes.

### High — authorization bypass through direct table writes

- **Objects:** initial-schema `member_admin_manage`, `member_self_update`, `profiles_self_update`, administrative write policies and inherited table grants; correction in migration `202609210027_audit_authorization_boundaries.sql`.
- **Scenario / actual result:** an authenticated Admin directly updated the Chair's `members.status` and `profile_id`. Both succeeded, leaving zero active connected Chairs. Profile email and roster fields also had direct write paths outside their approved workflows. Broader administrative table writes bypassed RPC validation, versioning, frozen-state handling and audit insertion.
- **Expected / impact:** role and history restrictions must apply to the database API, not just UI controls. An Admin must not disable the Chair or reassign privileged identities through a roster update.
- **Fix:** revoke direct INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER privileges on public tables from ordinary API roles. Application mutations already use RPCs; no direct Supabase table mutations were found in `src`. Existing SELECT grants, RLS policies and webhook service access remain unchanged. RLS was not weakened.
- **Evidence:** new `audit_authorization_boundaries.sql` reproduced the writes before the migration and rejects them afterward. All application workflow database tests pass with the tighter grants. TRUNCATE was an excessive SQL-role privilege, not a demonstrated unauthenticated REST endpoint.

### High — account linking bypassed the Admin-management restriction

- **Objects:** `approve_access_request`, `disconnect_member_account`; migration 027.
- **Scenario / actual result:** an Admin could disconnect another Admin and could approve an account onto an unlinked roster member that retained an active Admin role. Linking consequently conferred Admin access despite `manage_member_role` correctly rejecting Admin grants by Admins.
- **Expected / impact:** existing role membership must also protect identity-link changes; otherwise the narrower role-management restriction is bypassable.
- **Fix / evidence:** Admin/Chair target account links require the Chair; the existing Chair-disconnection prohibition remains. Synthetic tests demonstrate both denied Admin actions and successful audited Chair actions. These operations still need concurrent role/link-change coverage, discussed below.

### High — access-request identity evidence was caller-controlled

- **Object:** `submit_access_request`; migration 027.
- **Scenario / actual result:** an unapproved account supplied another email/name to the RPC, and those values were stored in fields presented as authenticated identity evidence. The server action used the correct identity, but callers could bypass that action.
- **Fix / evidence:** derive email and display name from the `auth.users` record selected by `auth.uid()`, ignoring the two legacy input values while retaining the RPC signature. The spoof regression now stores the synthetic account's actual email. Display names remain user metadata, not proof of a person's legal identity; approvals should not rely on a name alone.

### High — the eight-course limit was not concurrency-safe

- **Object:** `enforce_active_course_limit`; migration `202609210028_audit_grade_integrity.sql`.
- **Scenario / actual result:** two simultaneous course additions at seven active courses both committed, producing **nine** active courses. This can also conflict with the application's eight-entry submission limit.
- **Fix / evidence:** serialize additions on the member row before counting. The repeat test produced **eight** courses: one transaction succeeded and the competing transaction was denied. Other members do not share this lock. Reproduction and regression: `supabase/audit/course-limit-concurrency.mjs`.

### Medium — grade revisions could change original timing or fail after grading-type edits

- **Object:** two-argument `submit_weekly_checkin`; migration 028.
- **Scenarios:** moving a deadline and submitting a revision changed `original_timing` from on-time to late; changing a course from Letter to Percentage caused the alert calculation to cast historical `C` to numeric and abort submission. SQL NULL entries also created an empty current revision; inactive accounts lacked an explicit active-member check.
- **Fix:** retain the previous original timing, calculate revision timing against the effective deadline, compare numeric prior values only from Percentage snapshots, reject null/non-array/empty/over-eight entries, and require active membership.
- **Evidence:** `academic_operations.sql` reproduced the changed timing, invalid numeric cast and null-input acceptance before the fix. Expanded assertions pass afterward; the existing weighted GPA, Pass/Fail exclusion, comment-limit, immutable snapshot and one-current-revision tests continue to pass. These fixes do not impose a new historical-submission policy.

### Medium — an obsolete frozen-hours proposal remained actionable

- **Object:** `refresh_study_hour_assignment`; migration `202609210029_audit_study_hour_consistency.sql`.
- **Scenario / actual result:** frozen hours were 1; a revision proposed 3; another revision restored the original grades. The assignment still offered a proposal of 3 in `review_required`, allowing acceptance of an obsolete calculation.
- **Fix / evidence:** when the latest calculation again equals the frozen requirement, clear the proposal and return to `frozen`, without changing final hours. `audit_frozen_recalculation.sql` reproduced the failure and now passes all four assertions.

### Medium — current-week session editing disagreed with roles and timezone

- **Object:** `edit_own_current_week_session`; migration 029.
- **Scenarios / actual result:** a Chair without a separate Proctor role could log a session but could not edit it. Database-session `current_date` could also lock a week that was still current in the semester timezone.
- **Fix / evidence:** allow the documented Admin/Chair self-edit capability while retaining session ownership checks; calculate the date in the semester timezone. Synthetic timezone-boundary and Chair regressions failed before the change and pass afterward. Existing old-week and other-Proctor denials still pass.

### Medium — email delivery results could be silently lost or misreported

- **Files:** `src/features/email/actions.ts`, `src/app/email/page.tsx`.
- **Scenarios / actual result:** Supabase's returned `{ error }` from `record_email_send_result_v2` was ignored; the action could continue and show success after a message was accepted but its status was not persisted. Transport configuration was checked only after the batch entered `sending`. The generic error banner claimed nothing was sent, even when that was unknown.
- **Fix / evidence:** validate transport construction before queueing; separate provider acceptance from database acknowledgement; stop on uncertain persistence without resending or overwriting it with a false transport failure; show distinct partial/unknown outcomes. Five mocked action tests cover these cases. This is a contained reporting/stop-sending fix, **not** a complete durable email recovery implementation.

### Medium — analytics could silently truncate data; member detail mixed semesters

- **Files:** `src/app/analytics/page.tsx`, `src/lib/supabase/read-all-pages.ts`, `src/features/members/queries.ts`.
- **Scenarios:** analytics fetched all chapter submissions and grade entries without pagination before filtering. Even 14 members × 8 courses × 16 weeks is 1,792 entries, before revisions. Member detail enabled its history query when a semester existed but did not actually filter that query by semester. Individual trends could include inactive members absent from the displayed active-member population.
- **Fix:** scope analytics submissions/entries to the active semester and current revisions, paginate those and weekly session totals deterministically, and discard partial results on any read failure. Align member trends with the active cohort. Scope member-detail history to the selected active semester and custom reviews to the requested member.
- **Evidence:** mocked pagination returns all 1,792 synthetic rows at both 500- and 100-row provider page caps and stops without retry on a later-page failure. Two member-detail tests cover semester/review filters. Three local anonymous PostgREST requests accepted the nested relationship/filter syntax with HTTP 200 and no data. Live academic totals were deliberately not inspected. Other unpaginated screens remain a risk below.

### Medium — CSV exports did not guard formula-like user text

- **Files:** `src/features/administration/semester-export.ts`, `tests/unit/semester-export.test.ts`.
- **Scenario:** a course name or other exported text beginning with formula syntax was only CSV-escaped, not marked as text. Opening such cells in a spreadsheet can interpret them as formulas.
- **Fix / evidence:** quote and apostrophe-prefix formula-like text, including leading whitespace/control and full-width variants; preserve actual numeric values; quote alternate delimiters. Eight new synthetic cases pass. The archive manifest documents that the safety prefix changes exported text, not database records.
- **Limit:** spreadsheet behavior varies and re-saving CSVs can remove protection. This is not a universal guarantee for every spreadsheet/import workflow; import untrusted CSV columns as text. See [OWASP's CSV guidance](https://community.owasp.org/attacks/CSV_Injection).

## Risks and gaps not established as production failures

- **Exactly one Chair:** the partial unique index enforces _at most_ one active Chair role, while bootstrap/transfer establish one. Migration 027 closes the reproduced ordinary-user route to zero. It does not stop an infrastructure owner from deleting the Chair's Auth user: the profile/member foreign keys can remove its account link. A database-level active/connected-Chair invariant and documented emergency recovery need design/testing before claiming protection against every administrative operation.
- **Concurrent role/link changes:** the approval/disconnection fixes lock the target member, but `manage_member_role` does not consistently use that same lock. Role changes simultaneous with account linking require a coordinated locking/revalidation test. No race exploit was reproduced for this combination.
- **Double clicks / stale edits:** submit buttons already provide pending feedback. That is not durable idempotency. Grade retries create valid extra revisions; identical session logging or recurring-series creation can create duplicates. Many editable records lack an expected-version parameter, so stale forms can overwrite newer changes. Add idempotency keys/optimistic concurrency to demonstrated business operations, not automatic retry everywhere.
- **Cache/session safety:** authenticated clients are request-created; React `cache` is used for request-level reuse, not a global cross-user data cache. The proxy preserves refresh cookies/cache headers; protected context verifies the Auth user. Existing tests cover session failures and cache-header handling. This does not prove production cold-start/session behavior under real Google accounts.
- **Availability:** historical Supabase 504/provider failures remain unresolved. No production fresh-load stress test was run or authorized here. No cause is attributed to RLS, Vercel cold starts, connection pools or session hydration without new evidence. Privacy-safe diagnostics and fail-closed errors remain in place; no secret-key read bypass or new automatic retries were added.
- **Performance:** per-week `FOR UPDATE` in grade submission serializes different members submitting for the same week. Export launches many chapter-wide reads before semester filtering. Both are source-supported contention/work risks, not measured hosted latency causes. No speculative indexes or global caches were added. Pagination is not a transactionally consistent historical snapshot if records change between pages.
- **Scope semantics:** the “Chair” route guard deliberately admits Admins; real Chair-only RPCs recheck the actual role. Switching to Member/Proctor screens changes the workflow, not the user's underlying Supabase role grants. Do not describe this as a database-level impersonation sandbox.
- **Custom conversions:** review supports exclusion and treatment as Pass/Fail; a reliable custom conversion is described in grading documentation but is not implemented as a complete configurable workflow. It was not built during this audit.
- **Environment assurance:** Vercel deployment variables, GitHub branch protection/CI, real Google client configuration, mail-domain verification, retention/backups and restore procedures were not comprehensively revalidated. The local `test:e2e` configuration exists, but no `tests/e2e` directory is present.

## Verification and evidence inventory

- Baseline: **249 pgTAP assertions / 16 files passed**. This baseline missed the subsequently reproduced defects.
- Corrected state: **289 pgTAP assertions / 19 files passed** against the isolated clean replay database. Includes nonempty synthetic grade/GPA rows for Member, Proctor, same-chapter Chair, other-chapter Admin, pending and anonymous access.
- Clean migration replay: 001–028 replayed successfully from an empty public schema; baseline 001–026 compared exactly with captured production metadata. Migration 029 was then applied and tested on that replay database. Hosted migrations were not applied.
- Course concurrency: before correction both competing additions committed (9 active courses); after correction one was denied (8). Synthetic fixtures were cleaned up.
- Unit tests: **173 tests / 31 files passed**, including the new mocked action, pagination, member-scope and CSV regressions.
- ESLint, strict TypeScript, formatting verification, production build and `git diff --check` **passed**. The build is not a deployment.
- Application-schema SQL lint (`--schema public`): no SQL errors; two intentional unused-parameter warnings for the compatibility-preserved, ignored access-request identity inputs. An unrestricted lint run also flags pgTAP extension internals, including test-session temporary objects and legacy compatibility branches; it is not a clean all-schema lint result. The executable pgTAP suite itself passes.
- Local PostgREST relationship checks: three read-only anonymous queries returned HTTP 200 and empty results. No real records were printed.
- Manual browser: local login rendered; nine direct protected navigations redirected to login (`/`, Members, synthetic Member Detail, This Week, Study Hours, Analytics, Administration, Member Check-in, Proctor). These are anonymous route smoke checks, not an authenticated Google end-to-end test.
- No automated browser E2E suite ran: the configured test directory does not exist. No production stress run, new hosted OAuth round trip, mail-provider delivery test, real roster import, or full device/accessibility sweep occurred.
- Metadata/probe helpers: `supabase/audit/`. Generated schema-only snapshots: ignored `test-results/audit/`. `known-gap-probes.sql` reports observations, not passing acceptance criteria; its fixtures roll back. `replay-local.mjs` refuses to overwrite its named audit database.
- Final local cleanup verification: both isolated audit databases contain zero Auth users, members and audit-log rows. The empty audit databases were retained for reproducibility.

**Recommendation:** review and deploy the authorization fixes through a separately approved rollout before expanding real-member use. Complete the synthetic authenticated role/linkage matrix and decide the remaining date/assignment/email policies before calling the system production-hardened. This report establishes specific fixes and limits; it does not certify the entire application as bug-free.
